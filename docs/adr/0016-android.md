# ADR 0016: Android companion

**Decision:** Use Avalonia's Android activity lifetime with a reduced single-session touch UI and capability-selected Android log sources. A Play/Release build provides immediate own-app capture and, after explicit user pairing, full-device capture through Android Wireless debugging. A direct on-device `logcat` source remains available only when the process already holds `READ_LOGS`, such as an opted-in developer build; the production app never self-grants that permission.

**Alternatives:** A separate native UI would duplicate presentation behavior. Requesting `READ_LOGS` through the normal runtime-permission API cannot work because Android does not expose it as an ordinary user-grantable permission. Using Wireless ADB merely to run `pm grant READ_LOGS` for VisualCat was rejected: although technically possible after user pairing on some devices, it turns the debugging channel into a privilege-elevation mechanism and creates unnecessary Google Play policy and security risk. Requiring root, Shizuku, Accessibility, Device Owner, or a permanently connected computer was also rejected as an inappropriate default for a Play-distributed log viewer.

**Consequences and validation:** The app must state the actual capture scope before and during Live capture. Play/Release manifests exclude `READ_LOGS`; Debug or explicitly opted-in non-Play builds may retain it for the established developer loop. Full-device production capture requires the user to enable Android Developer options and Wireless debugging, pair with Android's six-digit code once, and leave Wireless debugging on while Live runs. VisualCat persists only the reusable ADB identity, encrypted in app-private no-backup storage with an Android Keystore wrapping key; the pairing code is neither persisted nor logged. The Android adapter exposes only a fixed `logcat` stream rather than a general shell command API, disconnects when capture stops, and applies bounded reconnect/resume behavior on transport loss. Resume uses logcat's numeric Unix-epoch `-T` form because zone-less wall-clock text is interpreted in the device's local timezone even when output is UTC. Every reader-started Live capture holds an unexported `dataSync` foreground-service lease with a private ongoing **Stop and save** notification; a first permission grant explicitly reposts an already-started notification that an OEM may otherwise suppress. Android's API-35+ six-background-hour limit requests graceful finalization and is disclosed before capture. The service is non-sticky and its notification contains no log or identity data.

A Play build also carries Google's in-app update client, which asks the installed Play Store over IPC whether a newer build exists and hands the reader the store's own update flow. It is the only Android capability here that is not about capture, it adds no manifest permission, and it is bound by the rule that an update may never end a running capture, since both Play flows restart the process. ADR 0019 records the decision and the privacy boundary; the adapter is `src/VisualCat.Android/PlayAppUpdateService.cs`.

The Wireless ADB dependency is security-sensitive and unaudited upstream. Every candidate that contains this path therefore requires physical pairing/reconnect/soak testing plus an Android AAB dependency, ABI, license, permission, and native-artifact audit. Historical Android reports that exercised externally granted `READ_LOGS` remain valid for that older transport but do not validate the Wireless ADB path. When targetSdk moves to Android 17 / API 37 or later, local-network permission behavior must be re-reviewed before release.
