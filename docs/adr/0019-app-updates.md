# ADR 0019: Store-mediated update checks

**Decision:** A Google Play build asks the installed Play Store, over IPC, whether a newer VisualCat is available, and offers the store's own update flow. This is not telemetry and does not weaken ADR 0017. Builds Play did not install are never checked automatically, and VisualCat never contacts a VisualCat-operated or third-party server to look for a release.

**Alternatives:** Doing nothing leaves users on old builds with no signal, and makes the twelve-tester closed-testing cadence Google Play requires unworkable — a tester who never learns a new build exists is not testing. Polling a GitHub release feed at startup was rejected: it is direct network egress from VisualCat to a third party, on every launch, from an app whose users handle sensitive logs, and it leaks an install fingerprint (IP, approximate time, User-Agent) that the Play path does not. It also cannot install anything without `REQUEST_INSTALL_PACKAGES`, a permission this product should not want. A user-initiated link to the releases page carries the honest part of that idea at no privacy cost, so that is what non-Play builds get.

**Why this is not telemetry:** ADR 0017 forbids transmitting log content and shipping enabled analytics. The boundary that matters is not "does any network traffic occur", which would be an unmeetable rule for an app distributed by a store — it is *who is talking to whom, about what, and on whose behalf*. Here VisualCat opens no socket, sends no identifier, and names no VisualCat endpoint; it makes an inter-process call to an app already on the device, which answers with a version code. The network work belongs to the Play Store, under an account relationship the user already has with Google in order to have installed the app at all. No session, log, file name, search, or device identifier is part of the exchange in either direction. A future feature that reported anything *about the user or their data* would still require explicit opt-in and its own privacy review.

**Consequences and validation:** `docs/PRIVACY.md` states what the check does, what it remembers locally, and that a side-loaded build is not checked. The Play Core client is licensed under the Play Core SDK Terms of Service rather than Apache-2.0 and is recorded that way in `docs/THIRD-PARTY-NOTICES.md`. The dependency adds no manifest permission, which `tools/package-android.ps1` asserts on every release build.

Two constraints shape the behaviour rather than the plumbing. First, **an update must never end a recording**: both Play flows kill and restart the process, which would leave a live capture unfinalized without the drain-seal-reopen that Stop performs. So an offer the reader did not ask for is never raised over a running capture, the store's screen-taking Immediate flow is never started during one, and a downloaded update reports that stopping the capture is what installs it — guarded in `AppUpdatePolicy` and again in the view, and tested at both levels. A background *download* during a capture is harmless and is allowed. Second, **the offer must never take the notice lane from a message the reader has not read**: that lane also carries export failures and the one capture outcome a reader cannot see for themselves, so an update waits for a lane that is empty or carrying an ordinary confirmation.

Dismiss means "not now" rather than "never", and it has to cover a downloaded update as well as an unstarted one: Play reports a finished download on every resume, so a prompt that ignored the snooze would be repeated until the reader agreed to the restart they had just declined. A higher version code is a different question and bypasses the snooze. What may not be recorded as a refusal is a report — a failure, a progress line, or "this build was installed from a file" — because a reader who clears one of those has not declined anything, and treating it as a refusal would silence a real update through a route they could never diagnose. The distinction is drawn in `AppUpdatePolicy` rather than in the view, because only the policy can tell an offer from a report.

The app cannot learn which Play track an offer came from — the API reports a version code and nothing else — so the UI names the reader's own channel, read from its own version string, and never the update's. Naming the offered *version* is possible only because this repository's version-code scheme is deterministic and invertible (`ProductInfo.VersionNameOf`); a code that does not decode produces "a newer VisualCat" rather than an invented version. That scheme was widened for this feature so an alpha/beta cadence can produce more than one build per version; see `docs/RELEASE-CHECKLIST.md`.

The real Play path cannot be exercised by `adb install`, in CI, or on any build Play did not install, so every rule that decides behaviour lives in platform-free code with unit tests, and the device loop drives Play Core's own `FakeAppUpdateManager` behind an off-by-default build constant. End-to-end validation against the real client requires internal app sharing and is a release-checklist item.
